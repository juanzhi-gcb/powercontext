# 技术说明：端侧 Embedding + seekdb 混合检索

## 1. 模型与量化

| 项 | 值 |
|---|---|
| 模型 | `Xenova/all-MiniLM-L6-v2`（MIT，Hugging Face 公开仓库） |
| 输出维度 | 384，`mean` 池化 + L2 归一化 |
| 量化方案 | ONNX INT8（Transformers.js `dtype: "q8"`） |

模型体积按同一口径统计 ONNX 权重文件（实际下载的 `Content-Length`）：

| 精度 | 文件 | 体积（字节） | 压缩比（相对 fp32） |
|---|---|---:|---:|
| fp32 | `onnx/model.onnx` | 90,387,606 | 1.00× |
| fp16 | `onnx/model_fp16.onnx` | 45,297,825 | 2.00× |
| **int8（实际使用）** | `onnx/model_quantized.onnx` | **22,972,370** | **3.93×** |

## 2. 端侧运行

- 运行时：Transformers.js 4.3.1（ONNX Runtime Web），模型与推理都在页面内。
- 后端选择：先试 `device: "webgpu"`；`navigator.gpu` 缺失或初始化失败时自动改用 `device: "wasm"`。界面徽标显示当前后端，悬停可见降级原因。
- 预热：加载后立即推理一次，把 kernel 编译开销移出首个用户请求。
- 服务端不参与推理：集合绑定的 embedding 函数实现为直接抛错，任何绕过浏览器的向量化都会失败。
- 模型可本地提供：`npm run models` 下载权重到 `public/models/`，由本服务提供，页面不再访问外部主机。

## 3. seekdb 使用

- 接入：`seekdb` npm SDK 1.4.0 嵌入式模式（`path`），原生运行时 `@seekdb/js-bindings`。
- 集合：`documents`，`dimension=384`，`distance=cosine`，稠密向量索引 + 全文索引同时启用。
- 写入：`collection.upsert({ids, documents, embeddings, metadatas})`，按 64 条一批；`upsert` 使重复导入同一文档 ID 幂等。
- 检索：`collection.hybridSearch({knn: {queryEmbeddings, queryTexts}, nResults, include})`，**两路候选的融合（RRF）由 seekdb 内部完成**，客户端不获取两路结果再拼接。
- 增量与刷新：只提交新增段落；写入完成后即可检索（实测导入后立即检索命中）。

## 4. 实测结果

环境：Windows 11 + Edge（headless）、WSL2 Ubuntu、Node 20.19；语料 8 段，查询 5 条标注问题。

### 4.1 量化前后检索质量（同一浏览器、同一模型、同一查询集）

| 精度 | 加载 | 8 段文档向量化 | 5 条查询向量化 | 目标文档名次 | MRR@5 |
|---|---:|---:|---:|---|---:|
| **INT8 (q8, WebGPU)** | 2,239 ms | 372 ms | 548 ms | 1,1,1,1,1 | **1.000** |
| FP32 (WebGPU) | 869 ms | 88 ms | 115 ms | 1,1,1,1,1 | **1.000** |

**质量变化：0**（两者都把 5 个查询的目标文档排在第 1 位，MRR 均为 1.000）。评测方法：页面内用同一份 `Embedder` 分别以两种 dtype 编码语料与查询，按余弦相似度排序，记录目标文档名次与 MRR。此集合规模小、指标已到上限，量化未表现出可测损失。

体积换来的收益是 3.93× 压缩；本地加载的图初始化时间（2.2 s vs 0.9 s）反而是 q8 更慢，因为 WebGPU 上 int8 需要反量化算子。

### 4.2 WebGPU 全流程（应用自身指标面板）

| 阶段 | 实测 |
|---|---:|
| 模型加载 + 预热（首次，含 23 MB 下载） | 132,232 ms |
| 模型加载 + 预热（本地权重） | 2,239 ms |
| 文档向量化（8 段，批 16） | 545 ms |
| 写入 seekdb（8 段） | 247 ms |
| 查询向量化 | 104 ms |
| **seekdb 混合检索（服务端计时）** | **3 ms** |
| 端到端（点击检索 → 渲染） | 153 ms |

首次加载的 132 s 全部由 23 MB 权重下载占据；权重落到本地后降到 2.2 s，说明瓶颈在传输而非推理。

### 4.3 WASM 降级（屏蔽 `navigator.gpu` + 禁用 GPU）

| 阶段 | 实测 |
|---|---:|
| 后端 | **WASM**（界面徽标明示） |
| 模型加载 + 预热 | 1,446 ms |
| 文档向量化（4 段） | 101 ms |
| 写入 seekdb（4 段） | 1,460 ms |
| 查询向量化 | 7 ms |
| seekdb 混合检索 | 91 ms |
| 端到端 | 102 ms |

降级后核心流程完整可用，首条结果仍命中目标文档。

## 5. 优化点

- **批处理**：向量化按 16 条一批、写入按 64 条一批。
- **预热**：模型加载后立即推理一次。
- **本地权重**：`npm run models` 把权重放到本服务，避免每个新浏览器 profile 重新下载 23 MB。
- **单进程托管**：生产模式下同一 Node 进程同时提供静态页面与 API。
- **幂等写入**：`upsert` 替代 `add`，重复导入不因主键冲突中断。
- **原生库加载**：Linux 上以 `LD_PRELOAD` 预加载 `libseekdb.so`，规避 Node `dlopen` 无法满足静态 TLS 预留的问题；数据库在启动时显式创建。

## 6. 复现

```bash
npm install
npm run models      # 下载权重到 public/models（约 113 MB）
npm run build
npm start           # http://127.0.0.1:8787
```

质量对比：`bench/bench.mjs`（Puppeteer 驱动本机 Chrome/Edge，通过页面暴露的 `window.__kb.Embedder` 依次以 q8 与 fp32 编码同一查询集，输出名次与 MRR）。
降级验证：同一脚本加 `--disable-gpu` 并在页面启动前把 `navigator.gpu` 置空，确认徽标变为 WASM。
## 7. 附加实测（同一环境，重复 5 次取中位数）

### 7.1 Embedding 批大小的吞吐收益

| 批大小 | 中位耗时 | 每段耗时 | 相对批 1 |
|---:|---:|---:|---:|
| 1 | 113 ms | 112.8 ms | 1.00× |
| 8 | 254 ms | 31.7 ms | 3.56× |
| 16 | 404 ms | 25.2 ms | 4.48× |
| **32** | **736 ms** | **23.0 ms** | **4.90×** |

批 1 → 批 32 的每段成本降到 1/4.9。应用默认用 16（25.2 ms/段），再往上收益递减但内存占用上升。

### 7.2 int8 与 fp32 的向量一致性（量化损失的直接度量）

同一批文档分别用两种精度编码，逐条计算余弦相似度：

| 指标 | 值 |
|---|---:|
| 均值 | 0.99259 |
| 最小 | 0.99006 |

即 int8 向量与 fp32 基线保持 **99% 以上方向一致**，这解释了为什么检索名次没有变化。

### 7.3 检索模式对照（8 段语料、8 条查询）

| 模式 | MRR@5 | 首条命中 | 中位延迟 |
|---|---:|---:|---:|
| hybrid（向量 + 全文，seekdb 内部融合） | 0.938 | 7/8 | 48 ms |
| vector-only | 0.938 | 7/8 | 46 ms |

**如实说明**：在这份语料上两个模式结果相同——8 条查询里有 7 条目标文档本就排第一，全文分支没有改变名次。要体现全文分支的价值，查询集需要专门包含精确词元（数字、缩写、专有名词），这是当前评测集的局限，不是实现差异。

### 7.4 首次查询与预热后查询

| 场景 | 耗时 |
|---|---:|
| 首次查询（模型已加载） | 142 ms |
| 预热后查询 | 140 ms |

模型加载时已做一次预热推理，因此首个用户查询不再承担 kernel 编译开销。

### 7.5 离线资源

页面的模型权重由 `/models` 提供，ONNX Runtime 的 wasm 由 `/ort` 提供（`node_modules/onnxruntime-web/dist`），两者都不再访问公共 CDN。
